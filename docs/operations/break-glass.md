# Break-glass access, revocation and rotation

Scope: reach and repair the Proxmox host (`godseye-wg`, WireGuard `10.20.0.1`, public `65.108.38.218`) when the
pro VM, the console/dashboard and the owner's workstation are all unavailable (DS05, DS14). No private key,
passphrase or token is stored in this repository; this document names where each one must live.

Status legend: **verified** = executed on the live host and recorded in
[host-hardening.md](evidence/host-hardening.md); **procedure** = documented from the Hetzner/Proxmox mechanics but not
exercised in the current state of the server.

| C. Hetzner Robot remote console / reset | Owner login to Hetzner Robot; remote console on request | Yes (out-of-band) | **Procedure**, not requested or tested |
| D. Rebuild from backups | A host-config archive and the VM archives (local pool or restic copy) plus the restic passphrase | Yes | Backups **verified**; restoring a VM to a new VMID **verified**; a full bare-metal rebuild is the DS14 drill that remains open |

Failure matrix: if the pro VM is down use A (the host and VMs 200/300 are unaffected). If the workstation is lost use
A from the laptop or the mobile peer, or B/C with the emergency key held offline. If WireGuard itself is broken
(for example a bad nftables change) use B, mount the root dataset and repair `/etc/nftables.conf` or `/etc/wireguard`.

## 3. Using each path

### Path A: second device (laptop or phone)

1. Enable the device's WireGuard tunnel (UDP to `65.108.38.218:51820`).
2. `ssh -i <key> root@10.20.0.1` (or the phone SSH client with the emergency key). Proxmox UI: `https://10.20.0.1:8006`
   (user `root@pam` or the owner account).
3. Check the host: `qm list`, `zpool status -x`, `cat /var/lib/godseye/status/host-health.json`.
4. Reach a guest: `ssh <admin>@10.20.1.10|10.20.2.10|10.20.3.10` from the host or through the tunnel; or
   `qm terminal`/`qm guest exec <vmid> -- <cmd>` from the host when a guest's network or SSH is broken.

### Path B: Hetzner Rescue (host OS unreachable)

1. Robot, server `EX44-1-LTD #3097071`, tab **Rescue**: OS `Linux`, 64 bit, select the **emergency** public key, Activate.
2. Tab **Reset**: automatic hardware reset (or the console command if the owner has requested a remote console).
3. `ssh-keygen -R 65.108.38.218` then `ssh -i <emergency key> root@65.108.38.218` (the rescue host key is new).
4. Import the pool without mounting it over the rescue system, then mount the root dataset:
   `modprobe zfs || apt-get install -y zfsutils-linux`, `zpool import -f -R /mnt rpool`, `zfs mount rpool/ROOT/pve-1`.
5. Repair what is broken (for a firewall lockout: edit `/mnt/etc/nftables.conf`, or disable the guard with
   `rm /mnt/etc/systemd/system/multi-user.target.wants/godseye-nft-guard.service`; for a WireGuard problem: `/mnt/etc/wireguard/`).
   For a boot problem: bind-mount `/dev /proc /sys`, `chroot /mnt`, `proxmox-boot-tool refresh`.
6. `zpool export rpool`, deactivate Rescue in Robot (it is one-shot), reset, then confirm path A before closing the ticket.

## 4. Revocation and rotation

Rule for every change below: keep one verified SSH session open, make the change, open a **second** session to prove
access, only then remove the old credential. Each step lists its rollback.

### 4.1 Revoke or replace a WireGuard peer (lost phone or laptop)

1. Immediate effect (runtime): `wg set wg0 peer <PEER_PUBLIC_KEY> remove`.
2. Persist it: delete that `[Peer]` block from `/etc/wireguard/wg0.conf` (copy the file to `/var/lib/godseye/rollback/` first).
   Do not use `wg-quick down/up`, which drops the other peers' sessions; `wg syncconf wg0 <(wg-quick strip wg0)` applies the file safely.
3. Prove revocation: `wg show wg0 peers` no longer lists it; the lost device can no longer ping `10.20.0.1`.
   `h07-break-glass-drill.sh` runs exactly this sequence with a temporary peer.
4. Replacement: generate a new key pair **on the new device**, send only the public key, add
   `wg set wg0 peer <NEW_PUB> allowed-ips 10.20.0.<n>/32,fd47:6f64:7365::<n>/128`, add the same block to `wg0.conf`, check a handshake.
5. Rollback: re-add the removed block from the copy.

### 4.2 Revoke or rotate an SSH key

1. Add the new public key to `/root/.ssh/authorized_keys` (append only), open a second session with it.
2. Remove the old line (identify it with `ssh-keygen -lf /root/.ssh/authorized_keys`); keep at least the emergency key.
3. Rescue key: replace it in Hetzner Robot (Key management) at the same time and on the offline copy.
4. After any private key was exposed also review `last -a`, `journalctl -u ssh`, and the Proxmox task log.

### 4.3 Rotate the WireGuard server key

1. `wg genkey` on the host into a root-only file, derive the public key, schedule `systemd-run --on-active=300s` to restore the previous config.
2. Update `PrivateKey` in `wg0.conf`, update the `[Peer]` `PublicKey=` line on **every** device, restart `wg-quick@wg0` only when a second path (Rescue or console) is available, because all tunnels drop.
3. Verify handshakes from two devices, cancel the rollback timer.

### 4.4 Rotate the restic passphrase or the B2 key

- B2 key: create the new key in the Backblaze console, rerun `h08-offhost-credentials.sh`, confirm `godseye-offhost-backup config` succeeds, delete the old key in the console.
- Passphrase: `restic key add` (new) then `restic key remove` (old) while the environment from `/etc/godseye/offhost-backup.env` is loaded, then update the escrow copy and `/etc/godseye/restic-password`.

### 4.5 Proxmox accounts

`pveum user list` shows `root@pam` and `lucas@pve` (Administrator). Rotate the password of each after any suspicion; the web UI is
only reachable through WireGuard. Enable TOTP for `lucas@pve` in the UI and keep its recovery keys with the other escrow items.

## 5. Owner drill (every quarter and after any peer or key change)

From each real device (laptop, phone on mobile data) with the workstation switched off:

1. Bring up its WireGuard tunnel; `ping 10.20.0.1` answers.
2. `ssh` to `root@10.20.0.1` with the key stored on that device; `uptime` works.
3. Open `https://10.20.0.1:8006`, log in.
4. Record date, device and result in the ledger. A device that fails any step is treated as unavailable until fixed, and the single-point-of-failure risk is logged.
5. Once per year (planned maintenance, all VMs restart): run path B end to end up to the point of mounting `rpool`, then reset back.

## 6. Known gaps

- `laptop` and `mobile` have not completed a handshake since the last host boot, so path A from them is unproven.
- Path B and C were not exercised on the installed system; the restic passphrase escrow and the Robot remote console are owner actions.
- The pro VM cannot be unsealed or restarted from the host alone: OpenBao shares stay with the owner ([openbao-custody.md](openbao-custody.md)).
