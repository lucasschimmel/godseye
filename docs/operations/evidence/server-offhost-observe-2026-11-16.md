## 1. Backblaze cleanup of cell prefixes (DONE)

- `pgbackrest stanza-delete` was not possible for `cells/414cc5e5-...`: its configuration and its cipher passphrase no longer exist (no OpenBao escrow entry either), and pgBackRest cannot open an encrypted stanza without the passphrase. The prefix was removed at object level instead with `p13-b2-prefix-tool.mjs` (S3 SigV4, key read from the environment on the VM; refuses anything that is not exactly `cells/<uuid>/`; dry run unless `--apply`).
- Finding: the bucket keeps **every version** (no "keep only the last version" lifecycle rule). The teardown of the disposable cells A and B in entry 019 had only hidden their objects (`stanza-delete` creates delete markers). Before cleanup, `cells/` held three prefixes: the orphan (7 objects, 3.8 MB), cell B (1589 keys, 3183 versions, 10.2 MB) and cell A (1606 keys, 3217 versions, 11.0 MB).
- All three prefixes were deleted version by version (7 + 3183 + 3217 versions). `usage` afterwards: `cells/` no longer exists; `pgbackrest/` 2080 keys, 2100 versions, 42.5 MB (control stanza).
- Control stanza `main`: `pgbackrest check` passes (WAL segment archived to B2) before and after; `info` shows `status: ok`.
- Retention: `repo1-retention-full` of the control stanza changed 4 to 2 (`/etc/pgbackrest/pgbackrest.conf`, owner postgres, 0600; `expire` ran, one full exists so nothing was removed). The template in `p06-pgbackrest-and-restore-drill.sh` follows. Per-cell stanzas take `fullRetention` from the project backup policy, whose default in `recovery-view.ts` is already 2 (contract range 2 to 4); no live cell exists.
- `p13-b2-retention-check.sh` (read-only) reports keys, stored versions and bytes per prefix, hidden-version overhead, control full count (must be at most 2) and any `cells/<uuid>/` prefix without a configuration directory. Result: `RETENTION_CHECK_PASS`.
- Not possible with the shared key: reading or setting the bucket lifecycle (`GET ?lifecycle` returns `AccessDenied`). Owner step (entry 023): Backblaze console, Buckets, the bucket, Lifecycle Settings, "Keep only the last version of the file".

## 3. Status publication into the VM (DONE)

- Direction: **host pushes, VM receives.** The VM has no credential into the host. The host holds one dedicated ed25519 identity (`/etc/godseye/status-push.key`, root 0600) and a pinned VM host key (`status-push.known_hosts`; the installer refuses to pin unless the scanned fingerprint equals the one read on the VM itself: `SHA256:rpdx...UkQqMo`).
- On `godseye-pro`: system account `hoststatus` (locked password, no other key), authorized key `restrict,from="10.20.1.1",command="/usr/local/lib/godseye/godseye-host-status-receive"` in a root-owned `authorized_keys` (the account cannot edit its own restrictions). The command accepts exactly `host-health` or `offhost-backup`, caps stdin at 256 KiB, validates the JSON shape with `jq`, and replaces the file atomically. A different command (`id`) is answered `unsupported target`.
- Output: `/var/lib/godseye-host-status/{host-health,offhost-backup}.json`, `hoststatus:godseye`, `0640` inside a `0750` directory. The service user `godseye` has primary group `godseye`, so no group change was needed; `runuser -u godseye -- cat` reads it. (`/usr/local/sbin` on the VM is root-only, hence the receiver lives in `/usr/local/lib/godseye/`.)
- Cadence: drop-in `godseye-host-health.service.d/50-status-push.conf` (`ExecStartPost=-.../godseye-host-status-push`) pushes after every 15-minute health run; the panel marks the file stale after 45 minutes.
- OpenBao trust: the listener certificate already carries SANs `openbao.godseye.internal`, `127.0.0.1`, `10.20.1.10` (the sentence about a missing 127.0.0.1 SAN in `openbao-custody.md` was stale) and the service environment has `NODE_EXTRA_CA_CERTS=/etc/openbao/bao.crt`. From the service environment `node` fetches `https://127.0.0.1:8200/v1/sys/seal-status` with full verification: `sealed=false`. No verification is disabled anywhere in the control API.
- Environment (managed by `p07-deploy-platform.sh`, preserved on later deploys): `GODSEYE_OBSERVE_ROOT_PATH=/`, `GODSEYE_OBSERVE_CELL_DATA_PATH=/srv/godseye/pg` (`df` readable by the service user), `GODSEYE_HOST_HEALTH_FILE=/var/lib/godseye-host-status/host-health.json`, `GODSEYE_PG_BACKUP_STATUS_DIR=/var/lib/godseye/pg-backup`.
