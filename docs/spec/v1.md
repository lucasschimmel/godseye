## Product intent and V1 completeness

Deliver the owner's private platform for deploying applications, operating their backend/data services, scheduling jobs, running Hermes skills, controlling AI costs and supervising professional/personal hosting. No n8n or visual modular automation builder is included. Inngest and code define jobs; Hermes executes agentic work; Laya provides local decision classification. The custom TypeScript SDK is accepted; unchanged Supabase API compatibility is not required.

The requested "V1 at 90%" means a near-complete coherent release, not a statistical security/feature score. All requirements in the catalog and all mandatory isolation/data controls must pass before V1 release. Engineering checkpoints may be partial and privately reviewed; they are not a reduced release target. Optional post-V1 items are explicit below and do not silently remove any requested essential capability.

### Autonomous workers and external persistence continuation

The implemented local E06 runtime separates the trusted jobs supervisor from the owner HTTP process.
Both use the existing PostgreSQL control journal; PGlite is unsuitable for concurrent independent
processes. The supervisor alone consumes the `local.jobs` adapter. Detached owner workers exclude
that adapter before validation, dispatch and lease reconciliation, and the supervisor excludes
unrelated infrastructure/delivery adapters. A cell subprocess owns its application listener,
signed Inngest SDK endpoint and first-party handlers; it receives neither the owner database URL
nor another cell's material. The OS-created IPC channel binds scope instead of a caller-supplied
project or public admission RPC. This is trusted-code process separation, not hostile-code sandbox
qualification.

Every application engine and the independent platform engine require their own authenticated
PostgreSQL workflow database and Redis instance. A missing, reused or unavailable configured
dependency must refuse startup; embedded fallback cannot satisfy this profile. PostgreSQL persists
engine configuration/history while Redis persists live queue/run state. Inngest's initial event
stream remains in-memory even with external stores, so durable source intent and Foundation
receipt acknowledgement remain required. Engine `/e` acceptance never proves durable domain
admission or business completion.

## Main journeys

**Create a project:** choose a template and resource profile; preflight capacity/domain/account dependencies; reserve cell resources; provision private cell networks/sandboxes/database/identity/files/jobs within the professional VM; deploy; verify health; reveal SDK configuration containing public URLs and references only. Failed steps expose the operation, compensation and retry path (F03-F04, T09).

**Ship a release:** repository event requests a build; policy isolates its inputs; a tested artifact becomes a preview; readiness/security/migration evidence enables promotion; production switches to the selected artifact; the timeline connects logs, jobs and usage. Preserve a compatible image and independent data recovery point (F08-F11, T10-T12).

**Run an operational skill:** Inngest triggers a scoped operation; rules/Laya prioritize inputs where appropriate; Hermes loads the selected trusted skill/version; tools run with the task grant; evidence and usage stream to the console; privileged/public side effects follow policy; unknown outcomes require reconciliation (F20-F31, T18-T29).

**Recover a project:** select a verified recovery point; reserve a separate restore cell; restore database and the associated file/config recovery set; validate identity/API flows; review timestamp gaps; promote explicitly; retain the old destination until the quarantine policy permits removal (F15/F37, T07/T30-T31).

## API and operation contract

Draft machine-readable boundaries are [project manifest](../contracts/project.schema.json), [operation](../contracts/operation.schema.json) and [action request](../contracts/action.schema.json). They are design schemas, not a running HTTP API. T34 validates their provider/API compatibility; T09/T18/T23/T37 validate persistence and lifecycle behavior.

All resources use platform UUIDs and a revision. Provider IDs live only in trusted mappings. Create/mutate requests require an idempotency key; resource updates also require an expected revision. A collision with different parameters returns 409. Pending long work returns 202 with an operation ID; the client subscribes or polls. Stale revisions return 409; validation 422; authentication/authorization 401/403; quota/rate 429; insufficient admitted capacity 409; degraded provider 503. Errors return a safe error code, operation/correlation ID and retry guidance, never secret values. These rules apply to every F03-F41 mutation.

Normal lifecycle: `queued -> validating -> running -> succeeded`. Work may enter `waiting` or `awaiting_approval`, then resume. Authorization/preflight failure ends in `failed`; cancellation becomes `cancel_requested` and only becomes `cancelled` after grants and execution are stopped. Uncertain external outcomes become `unknown`, then `reconciling`; only observed evidence or explicit owner resolution permits a final result/new retry. Cleanup is tracked separately and never disappears behind success. T18/T23/T24/T37 cover all transitions.

Lease fencing prevents an expired worker from applying a late result. Before an external side effect, persist intent and deduplication identity; after timeout, reconcile provider state. Automatic retries are permitted only for known safe/idempotent actions. An approval is bound to the intended action/parameters/revision and expires; the agent cannot approve itself. Keep read-only monitoring and previously authorized recurring checks automatic. Test with T18/T22-T24/T37.

## V1 action and actor policy

This table is mandatory behavior for F24/F34/F35 and T22/T24/T37. Unknown/unlisted action-intent combinations are denied until a versioned policy explicitly covers them. A standing grant is a stored owner-authorized definition tied to exact scope, allowed actions/resources, maximum budgets and expiry; an agent cannot create or enlarge one. Direct owner commands still pass schema, revision, capacity and audit checks. Fresh approvals expire after one hour and are invalidated by any change to the action digest or target revision.

| Action or intent | Owner | Scheduler/service/agent |
| --- | --- | --- |
| Scoped reads, telemetry and source research | Normal authenticated session | Allowed only by an existing scoped tool/grant |
| Approved recurring passive audits, log analysis, research, draft generation, backup jobs | May authorize the bounded definition once | Execute the unchanged authorized definition; no production mutation or publication |
| New/changed schedules, skills, integration configuration or agent task definitions | Explicit owner command | Cannot self-authorize; may propose for owner action |
| Nonproduction builds/previews/deploys and bounded test jobs | Explicit owner command or standing definition | Allowed only under the existing nonproduction grant and admission limits |
| Exact-scope production artifact promotion under F46 | Owner creates/revokes the bounded standing policy with passkey step-up; otherwise fresh action-bound approval | Trusted broker executes only after source/check/artifact/freshness/provider gates; agents cannot create or widen the policy |
| Production migrations, live restore activation, domain rerouting or privilege/policy expansion | Fresh action-bound approval with recent passkey step-up; F46 does not authorize these actions | Propose only; trusted broker executes the exact approved command |
| Project/cell quarantine or final purge, including expired quarantine | Fresh action-bound approval with passkey step-up; final purge needs a fresh approval after quarantine expiry | Cannot authorize; cleanup executor acts only under that approval |
| External publication | Fresh approval for the exact payload, destination and qualified connector | Draft/propose only; broker publishes after approval; unknown delivery is reconciled |
| Routine credential rotation | Owner command or preauthorized exact role-rotation definition | Trusted rotation service only, with no authority to widen SQL/grant scope |
| Cancellation, grant expiry, budget stop and protective suspension | Owner or approved safety policy | Trusted broker can revoke/stop within existing scope; agents cannot suppress safety actions |
| Global credential/hypervisor/provider recovery settings | Owner command with passkey step-up via private recovery path | Denied to project/agent identities |

Step-up must have occurred within five minutes before approving the immutable proposal. A credential broker/system executor verifies the owner record; possession of an `approvalId` or an owner-looking field does not bypass it. An expired approval cannot be auto-renewed. Cancellation and safety stops do not require approval to prevent an over-budget or revoked task continuing.
