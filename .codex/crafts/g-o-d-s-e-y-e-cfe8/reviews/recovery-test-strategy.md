Spec-first matrix drafted from `recovery-design.md` and AC-35–43 before reading recovery implementation. Baseline supplied by coordinator: 421 unit/integration cases, 21 browser cases, 47 curated mutation experiments; existing cases remain intact. Coverage and new mutation score are unmeasured.

## Risk and scope

Highest risks are activating physically cloned pending work, overwriting or adopting a source/foreign target, admitting insufficient capacity, and treating missing receipts or journal coverage as proof of safety. Tests must assert durable externally observable state and exact resource preservation, not only provider invocation counts. Synthetic provider qualification is explicitly fault-contract evidence, never native PostgreSQL, off-host, firewall, quota or all-service production qualification.

## Contract critique before implementation

1. Existing Foundation `effectKey` identifies a run-specific effect. It is not a stable business effect ID and cannot alone establish complete non-rewound application journal coverage. Activation must remain unavailable without an actual independently qualified coverage/reconciliation adapter; an empty fixture journal cannot silently establish completeness.
2. Existing Foundation epoch/grant revocation fences Foundation tasks. It does not prove old application processes, ingress, schedulers, outbox, Inngest/Hermes or broker material consumers have stopped producing effects. Activation needs exact independently observed old-source producer/egress fencing and a new non-rewound epoch; no boolean or owner-input proof suffices.
3. A restore destination must retain source PostgreSQL `system_identifier` and catalog names while using a new allocation and private physical mappings. Ordinary `DatabaseEngine` fresh provision/bootstrap or allocation-derived destination role/database names would corrupt the restore contract.
4. Recovery HOLD must be enforced inside shared authority/grant/dispatch hooks, not solely in recovery routes or metadata. Test normal app/database resume, generic Foundation queue, broker service and task material access. Restored snapshots and ordinary project/environment edits cannot clear the hold.
5. Source revision, exact physical allocation/provider generation, repository namespace, backup chain/target, recovery set and all finite capacity obligations must be bound into preparation/admission and rechecked after awaits. Target environment/allocation and reservation must commit atomically with idempotency; concurrent prepares/admissions cannot adopt an existing target.
6. Lost ACK, absence, cancellation, qualification drift and late completion provide no proof that a mutation did not materialize. Preserve exact target/hold/reservation as unknown or quarantined; reconcile read-only against the exact immutable scope, never retry destructive restore or replace a foreign resource.
7. `archive max filename`, backup process exit and a repository directory are insufficient recoverability evidence. Require exact independently authenticated backup/base/WAL interval/timeline/manifest metadata; missing WAL or coverage never activates restored jobs or source snapshot effects.
8. Recovery capability should expose data-restore verification separately from all-service activation availability. Missing file/auth/config snapshots and real private producer adapters are explicit blockers by default. Weekly full/daily differential preparation is policy, not proof of an active scheduling consumer.

## Execution order and boundaries

Write strict policy/compiler/schema cases first (small/medium), then shared admission/hold invariants (large), fault/restart/reconciliation cases (large), HTTP/client contracts (medium). The three earliest meaningful guards are strict execution-field rejection, default all-service activation denial, and lost-ACK reservation preservation. Native and browser files have separate owners. New files use `T-AC-xx` names and GAUNTLET provenance.

Run only targeted recovery files during concurrent implementation; coordinator controls full-suite execution. Reuse the existing curated mutation harness with a separate case list only after coordinator approval; select mutants that remove scope, freshness, hold, coverage or uncertainty guards and require an observable behavior failure. No second runner, fake full-score claim, external services, private material/config reads, global installation, production/server actions or modifications to unrelated tests.
