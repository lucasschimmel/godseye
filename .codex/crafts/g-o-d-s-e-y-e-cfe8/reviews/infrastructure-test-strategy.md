# Infrastructure inventory and isolated provisioning test strategy

Date: 2026-11-11. GAUNTLET / CRAFTS scope: local E02.S03, with E03 lifecycle integration only where required by provisioning. Production intent. Node24, Bun1.4.4, TypeScript, Vitest, Playwright, Drizzle/PGlite. Baseline supplied by the parent:215 passing unit/integration cases,16 browser journeys and18 selected mutations. No new implementation or infrastructure qualification is claimed by this document.

## Existing code and test boundaries

Reuse `FoundationEngine` in `packages/core/src/foundations.ts`: immutable plans, qualified adapter registry, durable enqueue/tick/reconcile, leases, grants, activation epochs and audit. `foundation-data.ts` provides owner freshness, environment ancestry and current execution validation; `journal.ts` serializes writes under `control_lock`. Current reservations in `foundation-plans.ts`/`foundation-queue.ts` concern monetary budgets, not host/pool CPU, memory or disk capacity. Do not treat them as already implementing physical capacity accounting.

`packages/core/src/operations.ts::requestOperation` executes local configuration validation only and refuses provisioning with503. `schema.ts::environments` currently stores planned CPU/RAM/disk fields; those are neither observed limits nor quota enforcement. `apps/console/src/routes/infrastructure.tsx` currently shows the planned AX41 topology and disconnected qualification state. New inventory/provisioning modules should reuse these boundaries rather than add an alternate in-memory job queue or an HTTP worker authority endpoint.

Existing foundation tests cover abstract adapter ticks, persisted idempotency, lease/epoch fencing and budget uncertainty. They do not prove actual Linux sandbox, network, disk quota or host reservation behavior. Existing owner/access tests cover identity and private-material boundaries. Preserve all those baseline behaviors.

## Meaningful local evidence and qualification gates

The parent observed Docker CLI installed but no reachable daemon. WSL Ubuntu and Docker Desktop distributions exist; that alone proves no runtime, firewall or quota support. Parent is investigating actual local lab availability. Do not install a host-wide daemon/runtime, change system networking, alter an unrelated WSL distribution, or enable a fallback from this strategy subtask.

A supported disposable Linux lab can provide real evidence if its runtime, filesystem, network family and firewall/backend are recorded. Standalone runsc under an isolated lab may prove selected sandbox properties without proving Docker/Compose deployment or the future professional VM. Docker Desktop tests may prove the mechanisms actually available in its Linux VM, not Proxmox/Hetzner routing. A gVisor test requires the effective runtime/platform, not a configured name alone.

Real persistent data limits require the selected mounted filesystem/quota mechanism. A writable image-layer size, named volume, reservation counter or tmpfs cap does not establish a quota on persistent bind-mounted project data. If that mechanism is unavailable locally, tests must positively prove admission refusal and report the real-quota family unqualified. Do not call a simulation a successful environment deployment.

No local evidence certifies Proxmox outer VM boundaries, guest-root containment, physical AX41 capacity, Hetzner public routes/NDP/MAC binding, public DNS/TLS, off-host recovery, multi-process PostgreSQL or the72-hour reference soak. One professional VM plus separate games/task guests remains the target; no per-project VM farm or nested Proxmox is introduced.

## Execution and ownership order

1. Publish exact production contracts, immutable policy schema and qualification evidence boundary. Tie the scenarios above to producer modules and AC aliases before test authoring.
2. Author parser/policy, inventory/refusal and PGlite admission/concurrency cases first. Use real store/consumer implementation and narrowly controlled provider faults.
3. Drive durable step/restart/reconciliation/quarantine faults and the post-I/O/caller-mutation races before broad UI closure. Preserve audit/reservation evidence in every uncertain case.
4. Exercise only qualified, owned disposable Linux lab capability, with allowlisted fixed images and bounded resources. Keep its result separate from contract-double tests and record unavailable capabilities explicitly.
5. Add owner HTTP/client and a small number of actual browser flows using independent project stores. Preserve215-unit/16-browser baseline and existing scope/admission defaults.
6. After source freeze, run focused tests then the full suite once without parallel heavy jobs. Extend the existing isolated curated mutation runner for genuinely meaningful new policy/capacity/dispatch invariants; do not count equivalent redundant guard deletion as a useful survivor or manufacture tests solely to kill it.

No hourly test-writing estimate is assigned before provider interfaces and lab capabilities are known. Concurrency arithmetic, dual-stack overlap and immutable scope are high-risk algorithmic candidates for bounded property/fuzz cases. Baseline coverage targets remain planned85% lines/80% branches and70% mutation on policy invariants; no percentage is inferred from selected experiments. Generated OpenAPI/vendor code and trivial wrappers are excluded from test authorship; actual authority, I/O and state transitions remain in scope.
